# Why the page freezes (Oct 28, freeze thread)

How it was measured: `scripts/v4-freeze.mjs` plays the rig's seeded game (you + 3 Normal bots, Relaxed, 1270x700, 4x CPU) and presses a key every 250 ms the whole game, rival turns and animations included, so every stretch where the page can't answer shows as input waiting. It records every long animation frame (scripts, forced layout) and a CPU profile of the whole game. Baseline: `freeze-base-named.md` (v0.9.3 source, unminified build).

## In plain words

1. Pointing at a "copy" space late in the game (Greatest Hits, Cover) froze the page for seconds. The "You'd get" line works the space out by playing it on a copy of the table. Past its limit it still split in two at every choice, so a long chain of choices became hundreds of copies. Worse, the card worked it out inside the screen's redraw, on the page itself. Measured: one Greatest Hits preview 8.7 s at full speed (about 30 s on a slow laptop); in the played game, a 3.1 s freeze when the pointer left a space in round III.
2. Every step of the game asked "can this player afford each member, every way they could pay, ranked against the contests" just to decide whether to light the card. That was most of the engine's time per step, on every bot step, every click and every "You'd get" branch.
3. The page is busy 68% of a whole game at 4x, so a click usually waits behind something. The table's redraw for each step is done in slices, but anything else that changes on screen mid-redraw (a hover opening, a card landing on the stage, a turn card folding) makes the browser throw the half-done redraw away and start over, and some of those force the whole redraw to run in one blocking piece.
4. Several things are recomputed on every step for every chair even when nothing about that chair changed (its "each round" income runs the engine's round start; its change check turns the whole player into text).

## Structural causes, with where (biggest freeze first)

1. **Previews explode and run in the render.** `src/engine/v4/preview.js:77` keeps branching two ways per choice past `NODE_BUDGET` (2^depth). `src/v4/game/Info.jsx` `usePreview(..., { now: true })` computes a cache miss synchronously in render (`HoverCards.jsx` SpaceCard/YoudGet, useCopyTargets; `ShopCards.jsx` ShopTicks), and the cache is keyed by state object, so every step misses. Profile: ShopTicks 4.6 s, usePreview 5.0 s inside long tasks; worst frame 3,131 ms (pointerout → render → previewSpace). The preview worker's watchdog (`Info.jsx` watch, 4 s) took a long job for a dead worker and moved all previews to the main thread for the rest of the session. **Fixed** (hard cap of 72 states; a space slow on this device waits for the worker instead of the render; the worker says it's alive while busy).
2. **Engine: the buy step ranks every way to pay just to test affordability.** `src/engine/v4/core.js:485-490` called `paymentChoices(...).length` (enumerates payment vectors, then `orderChoices` scores each against every contest via `rimCost`) for every shop card and tier, on every step that reaches a buy. **Fixed** with `memberPrice().afford` and an existence check for tiers (same answer, checked equal across seeded games). Greatest Hits preview 8,750 → 289 ms at 1x.
3. **Interrupted and forced-sync table renders.** The table commits each step via `startTransition` (GameScreen useTable.show). Default-priority updates during it restart it from scratch (React keeps one render in progress): timer setStates on the whole screen (`setTurnCard` fold at 2.6 s and 3.1 s, `setStolen`, toasts, `setOverBeat`), `finishPresentation`'s `setTable` (lag pod's lane), chain-end `AfterChain` bumps. `useSyncExternalStore` readers that render inside the table pass (`ActionStage`, not memoized, GameScreen.jsx:1634; `HoverCardLayer`, passed `state`; `ShopTicks` useHoverSpace) make React redo the whole pass synchronously when their store changes mid-render (react-dom `isRenderConsistentWithExternalStores` → `renderRootSync`); the stage store changes on every chain beat. Next to measure (renders begun vs committed counter is in).
4. **Per-step work that scales with the table.** `seatMemo.js` sigOf JSON-stringifies each player plus cards per state (3.9 s over the game) and calls `incomeOf` → `roundStartIncome`, an engine round-start run per state object (3.4 s); the table's merged view of a playing step is a second object, so it ran twice. **Fixed for income** (keyed by the players array, shared by both views). TurnCard's layout effect reads layout after writes (getComputedStyle, getBoundingClientRect, offsetHeight): 3.2 s self over the game.
5. **The press that skips a chain does the skip's whole cost before the click registers** (director.js installChainSkip → landAll, clearFlights, stageClear, finishChain listeners, layColumn). Lag pod's lane; flagged to it.
6. **Smaller:** chain start/end toggles `[data-chain]` which restarts every idle animation (lamp-b.css:573); one DOM node plus 2-4 Web Animations per flying coin (flight.js flyPath); `trail.feed` replays moves inside a useMemo when buys fold; the open log re-renders the whole log per step.

Ruled out: state size (about 20 KB), saving (off the input path), online snapshot parsing, the bots' choices (already in a worker for Normal; Hard can exceed the 1.5 s worker timeout at 4x and fall back to the main thread for good, botThink.js:62, to fix next).
